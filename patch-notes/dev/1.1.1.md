Built against Ziggfreed Common 2.3.0 on the Update 7 server line (0.7.x); the manifest floor moves to `>=2.3.0` and the server range to `>=0.7.0-pre.0 <0.8.0`. No behaviour change. The api artifact ships as `rpg-stations-api-1.1.1.jar` with the contract still at 10.

- **The 0.7 server line.** `ServerVersion` reads `>=0.7.0-pre.0 <0.8.0`. The engine matches pre-releases npm-strict, so the old `>=0.6.0-pre.13 <0.7.0` listed the jar as outdated on a 0.7.0 pre-release (a WARNING, a SEVERE roll-up and a red notice to players with the outdated-mods permission). New `ManifestTargetTest` reads the processed manifest with the engine's own `SemverRange` and checks that it admits the server jar the build compiles against and that line's release, and claims no later line.
- **The Ziggfreed Common floor is 2.3.0.** The floor moves with `ziggfreedCommonVersion`, and `ManifestTargetTest` pins it to the library jar on the test classpath. A 0.7.0 server with the 0.6.8-built 2.2.0 now refuses RPG Stations by name instead of loading it on a library whose page refreshes, spawn anchors and build checks fail silently there.
- **The api jar is 1.1.1.** The api artifact carries the release version (a release that adds nothing still ships one); `RpgStationsApi.apiVersion()` stays 10.
- **The item-quality contract in the docs.** On 0.7.0 a stack stores a quality only once one is set on it (`ItemStack.withQuality`, as a stamp does); otherwise `getQualityIndex()` answers its item's current quality. The `ActionInput` class javadoc and its `Quality` documentation string (so `SCHEMA.md`), `StationService.liveQualityOf` and `StationToolReadings` said a stack keeps the quality it was made with; they now say what 0.7.0 does. The `Quality` route and the Disenchanting Tables' protect list read through the same call as before.
