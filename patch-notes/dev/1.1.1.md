Built against Ziggfreed Common 2.3.0 on the Update 7 server line (0.7.x); the manifest floor moves to `>=2.3.0` and the server range to `>=0.7.0-pre.0 <0.8.0`. No behaviour change beyond three validator warnings, the ritual's session row, the Disenchanter's Kit's buff tile and one emote name (below). The api artifact ships as `rpg-stations-api-1.1.1.jar` with the contract still at 10.

- **The 0.7 server line.** `ServerVersion` reads `>=0.7.0-pre.0 <0.8.0`. The engine matches pre-releases npm-strict, so the old `>=0.6.0-pre.13 <0.7.0` listed the jar as outdated on a 0.7.0 pre-release (a WARNING, a SEVERE roll-up and a red notice to players with the outdated-mods permission). New `ManifestTargetTest` reads the processed manifest with the engine's own `SemverRange` and checks that it admits the server jar the build compiles against and that line's release, and claims no later line.
- **The Ziggfreed Common floor is 2.3.0.** The floor moves with `ziggfreedCommonVersion`, and `ManifestTargetTest` pins it to the library jar on the test classpath. A 0.7.0 server with the 0.6.8-built 2.2.0 now refuses RPG Stations by name instead of loading it on a library whose page refreshes, spawn anchors and build checks fail silently there.
- **The api jar is 1.1.1.** The api artifact carries the release version (a release that adds nothing still ships one); `RpgStationsApi.apiVersion()` stays 10.
- **The item-quality contract in the docs.** On 0.7.0 a stack stores a quality only once one is set on it (`ItemStack.withQuality`, as a stamp does); otherwise `getQualityIndex()` answers its item's current quality. The `ActionInput` class javadoc and its `Quality` documentation string (so `SCHEMA.md`), `StationService.liveQualityOf` and `StationToolReadings` said a stack keeps the quality it was made with; they now say what 0.7.0 does. The `Quality` route and the Disenchanting Tables' protect list read through the same call as before.
- **`UNKNOWN_CHANNEL` fails open per namespace.** `StationValidator.checkContributionChannels` warned for every channel nobody declared through `ContributionChannelRegistry` once anything was declared, so a pack posting to an optional mod's channel warned on a server that runs some other declaring mod but not that one. The decision is now the pure `StationValidator.warnsUndeclared(channel, declared)`: an undeclared `ns:x` warns only when a declared channel shares `ns:` (case-insensitive), so a typo inside an installed mod's namespace still warns; a channel with no namespace warns against any non-empty declared set, and an empty set still warns about nothing. The message echoes the declared channels of the same namespace. New `StationValidatorChannelNamespaceTest` tests the helper, never the global registry.
- **The station audit stays quiet about a loot table the mod gate refused.** `LOOT_UNKNOWN_TABLE` and a Lootable extension target's `EXTENSION_TARGET_UNKNOWN` ask Ziggfreed Common's `LootableValidator.modGateRefused` first, so a table whose file the mod gate refused is named nowhere, while a table nobody authored still warns.
- **A Steps program's session row fills by beats.** The session-progress row (`HudPanels.totalled` on the station's id) read `HudBarReading(remaining, feedableCyclesAtStart)`, and a Steps program has no pile (`feedableCyclesAtStart` 0), so a ritual's bar sat full from engage to stop. The authored-program `StationService.dispatchProgram` entry now reports `HudBarReading(programIndex, steps.size())` through the new `notifySessionBeat` when a pass suspends, on a fresh dispatch or on a resume that moved to another step (a walk or a hold re-entering the same step each frame reports nothing), and `seedSessionRow(s, programBeats)` seeds a Steps program at 0 out of its effective step count. A completed pass still reads full through `notifySessionCycle`, with the cycle count; each pass starts the bar over, so `Work.Queue` fills it once per piece. `moveSessionRow` takes the `HudBarReading`. A pile-draining session's fill is unchanged, and no schema or api changes. The docs gain "The session row" in `actions-and-steps.md` and a paragraph in `disenchanting.md`.
- **The Disenchanter's Kit shows one buff tile.** Each tier of `Server/ZiggfreedCommon/GearSets/RPG_Disenchanters_Kit.json` names a `Badge`, Ziggfreed Common 2.3.0's gear-set tier leaf: `{Pieces 2}` `RPG_Disenchanters_Kit_Badge_Pieces`, `{Armor 4, Effect}` `RPG_Disenchanters_Kit_Badge_Armor` and `{Armor 4, Held 1}` `RPG_Disenchanters_Kit_Badge_Held`. The set shows one tile, the badge of its highest tier that holds. The three effects are new under `Server/Entity/Effects/RPG/`, each `Infinite`, `OverlapBehavior` `Ignore` and `Debuff` false, carrying only a `Name` and a vanilla `StatusEffectIcon` (`Armor_Cloth_Silk_Hands`, `Armor_Cloth_Silk_Chest`, `Weapon_Spellbook_Grimoire_Purple`); the set engine puts them on and takes them off, so nothing else applies these ids. The set's look stays `RPG_Disenchanters_Kit_Look`. Names: `gearset.rpg_disenchanters_kit.badge_pieces`, `.badge_armor` and `.badge_held` in `rpgstations.lang`, in all nine languages.
- **The Open gesture's emote is renamed.** `avatarCustomization.emotes.RPG_Emote_Disenchant_Open.name` reads `Opening the Ritual` (was `Opening the Grimoire`; the double has worked empty-handed since 1.1.0). The key and the emote id are unchanged. The eight other locales in `avatarCustomization.lang` carry the new name too.
