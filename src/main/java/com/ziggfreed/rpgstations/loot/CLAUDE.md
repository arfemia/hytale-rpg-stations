# loot/

The loot model, its evaluator and the `Lootable`/`RollPool` stores are ziggfreed-common's (`com.ziggfreed.common.loot`); read its router, `zc-loot/src/main/java/com/ziggfreed/common/loot/CLAUDE.md` in ziggfreed-common, first. This package is only the station pass, and the one home of the station's grant-reporting rules.

- `Target:{Lootable}` extension rolls join zc's ONE table composition as a roll source (`ExtensionCatalog.registerLootableRollSource`, owner `rpgstations`, registered at plugin setup), so every site that rolls an extended table sees them, station or not; `StationLootEngine.resolve` is `LootEngine.resolve` plus its site label. Never merge rolls at a call site or in a station-only resolve. The order is pinned (`ExtensionCatalogTest`): the table's own rolls, its `ContributesTo` files', the extensions', then the ref's inline rolls. A test that resolves an extended table registers the source in `@BeforeEach`. `Target:{RollPool}` entries join zc's roll pool composition the same way (`registerRollPoolEntrySource`).
- A roll that authors no `Trigger` reads `"Default"`, and a station pass asks only `"Cycle"` or `"Completion"`, so it never fires at a station; pools draw on the cycle pass (asked with no trigger). Say so in docs and javadoc, and `StationValidator` warns on it (`LOOT_TRIGGER_NEVER_ASKED`); never change the runtime here.
- The three station reward kinds are ziggfreed-common `CollectingRewardKind`s registered ONCE into `RewardKinds.shared()` at plugin setup (`StationRewardKinds.registerInto`); a pass layers its `GrantResult` (the `Sink`) onto the subject with `Subject.withFacets`, so each grant, a nested `Lootable` table's included, collects onto that pass. They need the session and the cycle, so they never act from a handler, and outside a pass they count lost. Never build a registry per pass.
- A test that drives a pass with station kinds calls `StationRewardKinds.registerInto(RewardKinds.shared())` in `@BeforeEach`: the shared registry is process-wide and `RewardKinds.clear()` empties it.
- A pass always carries a non-null `Subject` (anonymous without a `PlayerRef`): a null subject switches off the whole reward leaf, the collecting kinds included. It reads its handles only through `handleAs` (the Player, then the layered `PlayerRef` and `Sink`).
- `rpgstations:output_items` is a fractional tally summed over the cycle and resolved once by `OutputItemResolver` (its `resolve` is ziggfreed-common's `StochasticCount.resolve`, never a copy of the rule); everything downstream reports the landed count (`OutputItemResolver.reportable`), never the rolled one.
- A pass's `Items` and `DropLists` sinks are ziggfreed-common's `GroundSpillSinks` (inventory first, then ONE pile per hand-over at the station block through `util/ItemDropUtil`, landed counts only what arrived); the station owns only that drop target. Never hand-build the pair again or roll a drop list through `ItemModule` directly: `StationValidator`'s drop-list probe rolls through `NativeLootService.tryRollNative` too.
- Every grant path counts what it landed on the HUD itself (`StationService.notifyItemGain`), never on the notification feed: the Produce phase reports only the recipe's deterministic `Yield`, so an uncounted bonus reads in game as not working.
- A `Commands` payout is invisible to every listener and never counts as `STATION_OUTPUT`; author a payout that must be counted as `Items`.
